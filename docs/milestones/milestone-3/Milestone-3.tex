\section{Project Overview}
%%----------------------------------------------------------------
The \textbf{AI Powered Pharmacy Management System} is a full-stack web application
developed as part of the Software Engineering course at IIT Madras.
The system digitises the day-to-day operations of a pharmacy by providing:

\begin{itemize}[leftmargin=1.2cm]
  \item A patient-facing interface for doctor discovery, appointment booking,
        prescription upload, and medicine ordering.
  \item A staff and admin dashboard for inventory management, order fulfilment,
        staff administration, and customer oversight.
  \item AI-assisted prescription digitisation using the Google Gemini API to extract
        medicine names and dosage from uploaded prescription images.
\end{itemize}

\subsection{Technology stack}
\begin{itemize}[leftmargin=1.2cm]
  \item \textbf{Backend:} Python, FastAPI, SQLAlchemy, SQLite (dev) / PostgreSQL (prod)
  \item \textbf{Frontend:} React (Vite), Tailwind CSS, Shadcn UI
  \item \textbf{Auth:} JWT via python-jose and FastAPI OAuth2 password flow
  \item \textbf{AI integration:} Google Gemini Developer API
  \item \textbf{API documentation:} Swagger UI embedded in the web app and OpenAPI 3.1 YAML
  \item \textbf{Testing:} pytest with an in-memory SQLite test database
\end{itemize}

\subsection{Sample: authentication registration endpoint}
\begin{lstlisting}[language=Python,caption={POST /api/auth/register -- backend/app/routes/auth\_routes.py}]
@router.post("/register")
def register(user_in: UserCreate, db: Session = Depends(get_db)):
    existing = db.query(User).filter(User.email == user_in.email).first()
    if existing:
        raise HTTPException(status_code=400,
                            detail="Email already registered")
    hashed = get_password_hash(user_in.password)
    user = User(email=user_in.email,
                hashed_password=hashed,
                role=user_in.role)
    db.add(user)
    db.commit()
    db.refresh(user)
    return user
\end{lstlisting}

\section{Testing Strategy}
%%----------------------------------------------------------------
\subsection{Type of testing}
Sprint 1 used \textbf{automated integration testing} as the primary testing approach.

\begin{itemize}[leftmargin=1.2cm]
  \item \textbf{Integration tests} exercise every API endpoint end-to-end through
        FastAPI's \texttt{TestClient}, which runs the full request-response cycle
        including database operations, authentication guards, and Pydantic validation.
  \item A separate \textbf{in-memory SQLite} database is created fresh for each test
        session, preventing test pollution and making the suite runnable without any
        external services.
  \item \textbf{Permission boundary tests} verify that unauthenticated or
        under-privileged callers receive HTTP 401 or 403.
  \item \textbf{Validation tests} confirm that Pydantic rejects out-of-range or
        missing fields with HTTP 422.
  \item \textbf{Mismatch and failure tests} intentionally trigger failure paths
        (e.g.\ missing AI API key) to document real-world environment-sensitive failures.
\end{itemize}

\subsection{Rigor and coverage}
\begin{itemize}[leftmargin=1.2cm]
  \item \textbf{97 test cases} covering all 12 API domains.
  \item Every domain has at minimum: a happy-path create, a happy-path read, an
        unauthorised-access attempt, and at least one invalid-input rejection test.
  \item Cross-user access tests confirm that customers cannot read or modify data
        belonging to other users.
  \item Admin-only and employee-only routes are tested with the correct role
        and with a wrong role to verify enforcement.
  \item Tests are organised into one file per domain (\apipath{test\_auth.py},
        \apipath{test\_inventory.py}, etc.) and share a common
        \apipath{conftest.py} fixture that seeds a minimal database state.
\end{itemize}

\section{User Reviews and Feedback}
%%----------------------------------------------------------------
\subsection{Testing methodology}
Informal user-testing sessions were conducted with three users representing the
primary user roles: a customer, a pharmacy staff member, and a pharmacy admin.
Each session was run as a think-aloud walk-through of the following flows:
registration, doctor listing, cart and order placement, and inventory management
via the Swagger UI.

\subsection{User feedback summary}
\begin{longtable}{p{0.18\textwidth}p{0.38\textwidth}p{0.36\textwidth}}
\toprule
\textbf{User role} & \textbf{Positive feedback} & \textbf{Improvement request} \\
\midrule
Customer & Fast and simple login flow; doctor listing is clear and easy to navigate & Better error message when prescription AI extraction fails; add a retry button \\
Customer & Appreciated the ability to view order history & Would like order status notifications \\
Staff & Inventory and order APIs responded quickly when tested in Swagger UI & Need a proper frontend screen for inventory management (currently API-only) \\
Admin & Creating and deactivating staff accounts worked smoothly via API & Wants a dashboard with sales analytics and low-stock alerts \\
\bottomrule
\end{longtable}

\subsection{Key takeaways}
\begin{itemize}[leftmargin=1.2cm]
  \item Authentication and doctor-listing flows are considered production-ready
        by all tested users.
  \item Prescription AI extraction error handling needs a friendlier user-facing
        message with a retry option.
  \item Frontend screens for inventory, orders, and admin workflows are the most
        requested feature for Sprint 2.
  \item Users were satisfied with the response times of all tested endpoints.
\end{itemize}
